Overview

Eleven-plus carriers, notified on every provider change.

Princeton PO must notify more than eleven insurance carriers whenever a provider changes. Done by hand, each submission took six to eight hours and carried a real error rate. Carrier timeliness is an NCQA compliance matter, so the cost of a miss is not just rework.

Before

Every carrier file built by hand

Each deliverable was assembled from conflicting source documents: a Standard spreadsheet, a Horizon spreadsheet, a CRM import, letters of intent, and an email. The rules lived in a few people's heads, and carrier timeliness sat under NCQA compliance.

After

One canonical model feeds every writer

A single normalized model feeds writers that generate every file, validate it, write to the CRM over API, and track to closure. A human reviews every batch, and the system captures what it learns along the way.

How it scaled

Scale is how cheaply it absorbs new work

The second workstream shipped in one to two weeks against the first's four to six. Five workstreams now run on the same core, because new work reuses the canonical model rather than rebuilding from scratch.

Role of the human

Automation assembles; the reviewer judges

Automation does the repetitive assembly. The reviewer owns the judgment call and approves every batch before anything reaches a carrier. Accountability stays with a person.

Reliability

Why the numbers hold.

Tested on every build

A mistake breaks the build, not a live submission.

A regression suite of more than 1,000 automated tests runs alongside an audit harness that verifies each build phase against its acceptance criteria. If something regresses, it fails in the pipeline, never in a file sent to a carrier.

Human QA on every batch

The judgment stays with someone accountable.

Automation handles assembly, but a reviewer approves every batch before it goes out. The system is built to assist the decision, not to replace the person making it.

Governance

How a wrong rule gets caught.

New carrier requirements surface constantly, and they were never fully documented, so the risk is codifying a misunderstanding into the system. Three controls prevent that.

01
Manual-first validation
A new requirement is run by hand once and confirmed accepted by the carrier before it is ever written into the system. Nothing is automated until it is proven correct on a real submission.
02
Compliance in the loop
New carrier requirements go to our compliance officer on a notify-unless-flagged basis: the team proceeds in compliance with the requirement unless a discrepancy is flagged.
03
Weekly review
Every submission is logged in a tracker and reviewed by the team each week against what actually went out, so anything sent-but-unlogged or logged-but-unsent is caught.

In a stricter compliance environment, this moves from notify-unless-flagged to documented sign-off before any rule goes live, with a formal change log. The control points already exist; tightening them is a process change, not a rebuild.

Resilience

Known failure points and fallbacks.

The system is built to fail in the pipeline, not in a submission, and every known failure point has a defined human fallback.

01
Address-validation API down
A human validates service locations directly on the provider's site, adding roughly ten to fifteen minutes per submission. No data is lost.
02
Agent-platform outage
The pipeline runs on Claude Code, so an extended outage is the hardest stop. The fallback is the manual workflow the system replaced; a documented revert runbook is a known next step.
03
Horizon glitches versus real errors
Horizon returns inconsistent errors, some not legitimate. A dedicated error logger records every Horizon error, what it means, and whether it is a true error or a system glitch, so recurring quirks are recognized instantly rather than re-diagnosed.
How the numbers are measured

The prep-time figure compares the manual workflow, multiple people building each file by hand over several hours, to the automated workflow, which assembles the same package in minutes with a single human review pass. The rework figure is calculated line by line at the field level, not submission by submission, so it reflects accuracy where errors actually happen. These are early numbers from a deliberately small window, tracked on every new submission as the sample grows.
